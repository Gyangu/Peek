# The icon set: migrating from Unicode glyphs to Lucide

## 1. What this fixes

### 1.1 The bug that set it off

The "split left/right" button on the panel action bar was drawn as `⊞`. Three
ambiguities stacked on top of each other:

1. **`⊞`'s common meaning is "add / expand"** — the Windows key, a boxed plus, the
   expand node of a tree control. The reader's first reaction is "new panel", not
   "split".
2. **`⊞` / `⊟` are an opposing pair in the general symbol vocabulary (expand /
   collapse)**, an opening and closing along one axis. Here they carry "left/right
   versus top/bottom", two **orthogonal** directions. Expressing a pair of
   orthogonal concepts with a pair of opposites leaves the reader unable to line
   them up.
3. **The shape itself points in no direction.** `⊞` is a four-square with both a
   horizontal and a vertical line, favouring neither left/right nor top/bottom;
   `⊟` has only a horizontal line, which does rather look like "split
   top/bottom". So exactly half of the pair happens to be right — which is more
   misleading than both being wrong, because it hands the reader a model that is
   self-consistent and does not extend to the other half.

### 1.2 The real disease is not in that one button

**Unicode simply does not contain the character "split left/right".** The author
did not pick the wrong one; they picked the nearest shape out of a set that does
not contain the target concept. The same disease has already recurred once in this
repository, and **it was written down at the time** — that passage in
`TreeView.tsx` about the node glyphs:

> ⛁ ❏ ▦ ◫ ◪ ⧉ ◇ — a set of symbols the reader is being asked to tell apart, where
> ◫ and ◪ differ only in which half is filled. … If these ever become hard to
> distinguish, this note says it was foreseen, and what the fix is: a size, rather
> than a different glyph.

The prescription that note wrote ("a size") was right at the time, because there
was no other option at the time. There is now, so the prescription changes: **what
is being swapped is not the size, it is the set**.

Two further costs exist only under the Unicode approach:

- **The glyph depends on the font.** `⛁ ⧉ ◪` fall in obscure blocks, and their
  rendering depends on what fonts the system has installed. That they are
  distinguishable on the development machine does not mean they are on a user's,
  and no test can see this.
- **Type size is the only adjustment knob, and the type scale has taken it.**
  After the typography baseline (§30.5) pulled the smallest size up to 12px,
  TreeView's disclosure caret and its node glyphs were forced onto the same rung —
  a design that relied on "one rung apart" has nowhere to go on a two-rung ladder.
  SVG sizes are orthogonal to the type scale, so this conflict disappears by
  itself.

### 1.3 Boundary (explicitly not done)

- **Keyboard symbols do not move.** `⌘ ⌥ ⇧ ⌫ ⌃` are the names of keycaps, not
  icons. They have to be those exact characters, and turning them into SVG is
  wrong. `AppearanceSection`'s `⌘+ / ⌘− / ⌘0`, `DataGrid`'s `ROWNUM_TITLE`, and
  the shortcut spellings in comments throughout are all kept.
- **Characters inside pure-text attributes such as `title` / `aria-label` do not
  move** — an element cannot go there.
- **Characters inside `<option>` do not move.** A hard constraint only discovered
  during implementation: `<option>` may contain text only, no element of any kind,
  and therefore no SVG. The one place `ChatView` marks the permissive permission
  modes with `⚠` has to stay — and that `⚠` is not decoration: those modes used to
  be marked by colour alone, which for a reader who cannot separate warn from the
  foreground colour is no marking at all, and a collapsed `<select>` shows one item
  only, so the colour has nothing to be compared against. This exception is
  **booked by location, not by glyph** (see §2.5): booking it by glyph would permit
  drawing another warning triangle anywhere, while the other nineteen places can
  all hold an element.
- **No semantic layering, theming or animation for icons.** This round swaps
  material only; it does not invent mechanisms.
- **No control variant, size step or colour changes.** Icon size is a new,
  orthogonal fact and does not touch the two steps `CONTROL_SIZES` already has.

## 2. The plan

### 2.1 Why Lucide

| | count | licence | how it lands in this repository |
|---|---|---|---|
| **Lucide** | ~1600 | MIT | linear / 1.5px stroke / 24 grid, the register of a tool-shaped desktop app; ESM per-icon exports, only what is used gets bundled |
| Phosphor | ~9000 | MIT | 1500 × 6 weights. The weight axis is of no use here, and what it buys is 6× the selection cost |
| Tabler | ~5900 | MIT | style close to Lucide's, larger set; a smaller community and ecosystem |
| Material Symbols | ~3600 | Apache-2.0 | a variable font, Google's visual language is heavy and does not suit this window |
| Heroicons | ~300 | MIT | sharp, but cannot cover TreeView's 11 node kinds |

The practical reason for Lucide is **enough and not more**: a database client does
not need 1600 icons, and the extra count in Phosphor / Tabler buys nothing here
except a longer time spent choosing.

**Iconify is rejected**: it is an aggregation layer (200,000+), whose upside is not
locking into one icon set and whose downside is a runtime network request by
default. Inside an Electron renderer that means configuring an offline bundle, and
it conflicts with this repository's "the artifact is the truth" audit line — a
lazily fetched icon set is one whose eventual output the build-time audit cannot
see.

**The decisive point**: Lucide has `columns-2` (a vertical divider) and `rows-2` (a
horizontal divider). The difference in shape between that pair **is the direction
itself**, with no "add / collapse" semantic contamination. All three of §1.1's
ambiguities go at once.

### 2.2 Icons are not imported directly at the call site

Writing `<Columns2 />` at the call site is the least effort and is wrong, for the
same reason this repository does not let call sites write colours: **"which concept
uses which icon" is a spec, and a spec can only exist in one place.** Scattered
across 20 files, the next person picking a second icon for "close" has no way to
discover the first already exists — which is the same story as the three
"destructive" buttons the control layer
(`docs/design/2026-08-02-control-spec.md`) was set up to clean out.

So, two layers:

**`ui/icons.ts` — the map from semantic name to icon, the single source of truth.**

```ts
import { Columns2, Rows2, X, … } from 'lucide-react'

export const ICONS = {
  'panel.splitRow': Columns2,   // a vertical divider = split left/right
  'panel.splitCol': Rows2,      // a horizontal divider = split top/bottom
  close: X,
  …
} as const

export type IconName = keyof typeof ICONS
```

The keys are **semantic names**, not shape names. The call site says "a close goes
here", not "an ✕ goes here". Changing the icon, changing the icon library, or
changing the shape for one concept only touches this table; the call sites do not
move a line. The keys for action icons reuse the Command Bus vocabulary directly
(`panel.splitRow`), aligned with the i18n keys and `data-peek-action`, so that
"what this button is called, what it announces, and what it draws" all share one
name.

**`ui/Icon.tsx` — pinning size and colour down.**

```tsx
<Icon name="panel.splitRow" size="md" />
```

- **The size comes from `spec.ts`'s `ICON_SIZES`**, and call sites may not pass
  pixels. Same reasoning as `CONTROL_SIZES`: a size that "depends on what the call
  site wrote" is not a size.
- **`color` is always `currentColor`**, decided by the container's text colour.
  This is more than convenience: `render-probe` measures contrast by reading pixels
  back out of the framebuffer, and only an icon that inherits the text colour can
  be **covered** by the existing contrast audit; an icon carrying its own colour
  becomes a blind spot for it.
- **`aria-hidden` is always true.** An icon is never the accessible name. The name
  comes from `<Button>`'s `label` or from sibling text — which is already the
  situation today (an `aria-hidden="true"` `<span>`); it just moves from "every
  call site remembers to write it" to "nothing else can be written".

### 2.3 Size steps: two, pinned onto the control steps

`spec.ts` gains:

```ts
export const ICON_SIZES = {
  md: 14,   // an icon inside a 24px control
  sm: 12,   // an icon inside a 20px control, and inline
} as const
```

The step names are **deliberately the same as `CONTROL_SIZES`'s**, so that which
step an icon inside `<Button size="sm">` takes needs no second decision —
`Button` passes the rung down itself, and the call site writes no `size`.

14 / 12 are derived from the box, not picked: after subtracting the strokes on both
sides and the visual breathing room, 14px makes the icon occupy about 58% of a
24px icon button's width, the usual density for a linear icon in a square button;
larger and it hits the edges, smaller and it floats as a dot inside a 24px box. The
20px step lands at 12px by the same proportion.

**Note that `ICON_SIZES` goes through element attributes (`width` / `height`), not
a class.** This is deliberate: a Tailwind size class would be compiled by the
scanner into a real rule, and `audit-shipped-css.mjs` requires every rule to have
an element wearing it — icon sizes going through attributes bypass that ledger
entirely and add not one line to the style layer.

### 2.5 Holding it with a test

After the migration, `renderer/__tests__/` gains one: **no "pictorial glyph"
character may appear in rendered JSX text** (the geometric-shapes, arrows and
miscellaneous-symbols Unicode blocks), with only the keyboard-symbol group on the
allowlist.

This test is the only thing in this change that can prevent a recurrence. Without
it, when the next author needs an icon the nearest path is still to type a
character — exactly as in §1.2. It lands as `__tests__/icon-set.test.ts`, and four
decisions are worth recording:

- **Blank the comments before reading.** This test's own description names nine of
  the banned glyphs, and `TreeView`'s comment still holds the old seven. String
  literals are **kept**, because "a glyph inside a template literal" is precisely
  the shape to be caught, while `title="⌘/Ctrl + Enter"` is precisely the shape to
  be let through.
- **What is banned is Unicode blocks, not the handful of characters used this
  time.** Same reasoning as the other bans in this directory that have been
  rewritten: a spelling list is only as long as what somebody remembered, and the
  next author will reach for a glyph that never appeared here.
- **Keyboard symbols are picked out by code point individually.** `⌘⌥⇧⌫⌃⏎⎋` sit
  inside the arrows and technical-symbols blocks, and narrowing the ranges cannot
  exclude them; they have to be named.
- **Exceptions are booked by file, each must carry a reason, and the reason's
  length is asserted.** "This one is fine" is a judgement, and a judgement that was
  never written down looks identical from the outside to an oversight. A second
  test watches the exceptions from the other side: once a file no longer renders a
  glyph, it demands the entry be deleted — an exemption nobody needs is where the
  next glyph hides.

This test was also **verified in reverse**: put `✕` back in `Toasts`'s icon and it
goes red immediately.

A third was added along the way: **every name listed in `ICONS` must have a
user**. The table is static, so listing something bundles it, and the larger cost
is that "list them all now in case they are needed later" stops the table being the
answer to "what concepts does this application have" — the same argument
`audit-shipped-css.mjs` makes about rules nobody wears, one level up.

### 2.6 A category found only while wrapping up: the label is a `string`

Everything on the list above is "a glyph written in JSX". Asking afterwards
"is that all of them" turned up **a completely different kind of escapee**: the
glyph is not in JSX but inside a **label whose type is `string`**, where an element
cannot go at all. Three places, two outcomes:

**`autoRefreshMenu.ts`'s `✓` — fixed, and more than the icon was fixed.**

It concatenated the check mark in front of the menu item's text: selected was
`` `✓ ${text}` ``, unselected was three spaces, `` `   ${text}` ``. Three defects
stacked up, and only the first is an icon problem:

1. the check is a character, because a string cannot hold an element;
2. **alignment by spaces**, which only aligns in a monospaced font — and this menu
   is not monospaced;
3. **the way a screen reader is told which item is current is by hearing a check
   mark read out** — that is, it is not told at all. Every item is an ordinary
   `menuitem`, and not one of them claims to be selected.

So the correct fix is not "swap the check for an Icon", it is taking **"which item
is in effect" out of the text and making it state**: `MenuItemNode` gains
`checked?: boolean`, `<Menu>` takes responsibility for drawing the check and for
reserving a check column across the whole menu (a column that only takes space on
the selected row would make the other labels jump sideways), and the `role` becomes
`menuitemradio` + `aria-checked`. `MENU_ITEM_BASE` therefore changes from `block`
to a horizontal flex layout — an item that can carry a check has two cells.

Its test was fixed along the way: it asserted `label.startsWith('✓')` and now reads
`checked`. Besides being brittle, the old assertion had a subtler problem — any
label beginning with a check mark would satisfy it.

**The two `⚠`s — kept, and deliberately.**

The two `⚠`s on the permissive agent modes in Settings sit on `<Segmented>` option
labels, whose type is `string`. This is **technically fixable**: give `<Segmented>`
an icon slot. The reason not to is consistency: the same two modes appear once more
in `ChatView`, where they are inside an `<option>` and **can never** hold an
element. A warning drawn as an icon on one side and as a character on the other is
worse than the same character on both.

This judgement is recorded in the test's exception table, and the exception table
is **booked by file rather than by glyph** — booking it by `⚠` would permit drawing
another warning triangle anywhere, while every other place can hold an element.

### 2.7 The test missed half of it itself

The reason the category above could survive until the end is that §2.5's test
**only scans `.tsx`**. `autoRefreshMenu.ts` is a `.ts`, and the whole of
`i18n/messages/` is `.ts` too. A rule of the form "X may not be rendered anywhere",
if it reads one extension only, is a rule about that extension.

It has been extended to `.ts`, and verified in reverse (put `✓` back and it goes
red immediately).

One more category has to be let through after the extension: **arrows in prose**.
`←→↑↓` have two uses in this repository that are both textual — `keys/chord.ts`
uses them to spell the arrow keys' names, and prose uses them to write a navigation
path ("Settings → Databases").

**This leaves a known hole, written down rather than hidden**: if anyone again uses
a bare `→` as the "next page" icon, the test lets it through — and that is exactly
what `TableView` used to do. Code points cannot tell them apart, only position can,
and this scanner reads text rather than a render tree. If a cheap way turns up it
gets fixed; until then the hole is one glyph wide, and it is written in the test's
comments. **This is the difference between a limitation written down and an
accident.**

### 2.8 Two things the user spotted at a glance, and the lesson they share

After the migration, the user held up a screenshot of the chat rail's header and
said "the sizes are inconsistent, it looks strange". Three buttons: `＋`, refresh,
`›`. Two defects stacked up, and **both existed before this migration and were
invisible before it**.

**Defect one: only the middle one is an icon.**

`＋` is U+FF0B (a fullwidth plus, from the halfwidth-and-fullwidth block) and `›` is
U+203A (from general punctuation). Both are nowhere near the symbol blocks §2.5
bans, so the test let them through. And they **are being used as icons**.

The consequence is not theoretical: **a glyph's size belongs to the font, an
icon's size belongs to the spec**, and a row mixing both cannot be aligned.

The fix is to add a `DRAFTED` category to the ban — characters that are not
pictures but have been conscripted into doing a picture's job. The criterion moves
from "does this character look like a picture" to "is what it is doing here a
picture's work", and which block Unicode filed it under has no say in it. ASCII's
`+` and `-` are deliberately kept out of this category: they are arithmetic, they
appear in real sentences, and banning them would misfire on every string containing
a plus sign; the fullwidth twins hold no second job in this repository.

Adding it immediately caught four more places **I had not seen**: `Sidebar.tsx`
has the identical trio (`‹ › ＋`), plus a line of text, `Use ＋ in the top right to
add one`. That line was changed in passing to say "click the top right to create
one" — **a hint that draws the button goes stale the moment the button's styling
changes**, and its `＋` and the thing on the button were never the same object
anyway.

The sidebar and the chat rail collapse in **opposite** directions (the left panel
retracts left, the right rail retracts right), so the same chevron means "collapse"
on one side and "expand" on the other, and one shared `collapse` name cannot be
right. Four names, each taken directly from an existing i18n key.

**Defect two: three icons, two button shapes.**

The `＋` and refresh buttons **did not declare `icon`**; only the collapse one did.
`icon` swaps the whole shape of the step for a square with no padding, so the other
two kept a text button's horizontal padding around a 14px icon — the same icon, two
widths, uneven spacing.

**Both buttons were wrong before the migration, and nobody could see it.** A `＋`
sitting in a text-shaped button just looks like "a button with a small character in
it"; once it is a real icon, the same thing looks like a defect. Unifying the icons
is what made the non-uniformity of the shapes **legible** — the usual way the other
half of a thing surfaces once one half is fixed.

A test was added too: **a `<Button>` whose content is only an `<Icon>` must declare
`icon`**. One exception (`PanelTabs`'s tab close, which is `aria-hidden`, so the
label `icon` forces would be a name nobody can read), which likewise has to carry a
reason and is likewise watched by a test checking the exception still holds.
Verified in reverse.

## 3. Trade-offs

**Why not just fix that one button.** Swapping `⊞` for `▥` is a two-minute job and
does resolve the ambiguity. Not doing it, because it leaves the disease in place:
the next icon still has to be picked out of a set that does not contain the target
concept, and `TreeView`'s note proves this is not hypothetical — the repository has
stepped into the same hole twice, and the second time the record of the first was
sitting right there.

**Why not draw the SVGs myself.** Thirty icons can be drawn; thirty icons drawn to
a consistent style cannot — stroke width, cap shape, corner radius and optical
centre of gravity, keeping those four consistent across 30 icons is a full-time
designer's job. Lucide's value is not that it has icons, it is that its 1600 icons
**are one person's calibration**.

**Why semantic names rather than lucide's names.** One more layer of indirection.
What it buys is "changing an icon does not touch the call sites", plus a readable
list: the `ICONS` table itself answers "what concepts does this application have",
while `import { X, Columns2 } from 'lucide-react'` scattered across 20 files answers
nothing.

**Why no generic icon-button component.** `<IconButton name="close" />` was
considered. It was rejected because it would **create a second entrance to the
control layer** — `<Button variant icon label>` is already that entrance, and this
repository has just spent a whole round converging three parallel "destructive
buttons" into one. `<Icon>` does icons only; buttons are `<Button>`'s business.

**A cost accepted: bundle size.** lucide-react exports per icon as ESM, so using 30
bundles 30, each about 200–400 bytes of path data, on the order of under 10KB and
negligible against an Electron artifact. But `ICONS` is a **static map**, meaning
every icon listed in it enters the artifact — so the table holds only what is
actually used, and "list them all now in case they are needed later" is not
allowed.

## 4. Verification

1. `pnpm --filter @peek/desktop typecheck` — `IconName` is a closed union, so a
   mistyped semantic name goes red at this step.
2. `pnpm test` — the point is that three existing audits must still be green:
   - `control-spec.test.ts`: `<Button>`'s className fence (icons are children and
     should not be affected, but `Gallery.tsx` changed and needs rechecking);
   - `theme-contrast.test.ts` / `type-scale.test.ts`: after `TreeView` loses two
     type-size-driven glyphs, the type scale's assertions must not lose the thing
     they assert on;
   - the new "no pictorial glyphs in JSX".
3. `pnpm --filter @peek/desktop build` — `audit-shipped-css.mjs` (no rule in the
   artifact that nobody wears, no colour outside `@theme`) and
   `audit-package-boundary.mjs` must pass. Lucide is expected to have zero effect on
   both, **but this is exactly the kind of expectation that only counts once it has
   been run**.

   Run: both substantive rules pass. Lucide's zero effect on the style layer has a
   structural reason and is not luck: its package is in `node_modules`, and
   `styles.css`'s `@source './'` points only at `renderer/`, so Tailwind's scanner
   **cannot see it at all** — and "the scanner read bytes it should not have" is the
   very hole this repository has fallen into six times. The icons themselves carry no
   CSS either: the shape is element attributes, the size is element attributes
   (§2.3), and the colour is `currentColor`.
4. `probe:render` — icons inherit `currentColor`, so framebuffer contrast should not
   change; if some icon button's contrast drops, it did not inherit the text colour.

   Run, all passing: 88 text/background pairs graded across the run, 84 of them
   re-read under `:hover` / `:active` / `:focus`, worst 4.89:1.
5. **Look at the Gallery with human eyes**: the dev build renders every variant ×
   state × size at the bottom of the settings dialog's About section. This is the
   only way to confirm whether 14px / 12px are right in a real window — the first
   four cannot measure "looks good".

   Done. `render-probe`'s fixture already renders the Gallery as a pane, so taking
   its `buildProbePage` to stand up a window and screenshot it is enough; there is no
   need to open the settings dialog by hand. Both steps hold up in a real window:
   `md`'s icon occupies about 58% of a 24px button's width, `sm`'s the same
   proportion in a 20px button, and across the five variants' icon buttons side by
   side no icon reads as too large or too small.

   One pit, written down to save stepping in it again: **in Electron's ESM main
   process there must be no top-level `await` before `app.whenReady()`**, or it never
   resolves. `probe-main.mjs`'s file header says exactly this, and it had been read
   past — this document can cite it only because it was finally read on the way back.
