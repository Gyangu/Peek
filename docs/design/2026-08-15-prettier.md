# Adopting prettier

## 1. What this fixes

As of today the repository holds 636 `.ts` / `.tsx` / `.mjs` files across 164,000
lines with **no formatter and no linter at all** — no eslint, no prettier, no
biome, not even an `.editorconfig`.

The style is nevertheless uniform: two-space indentation, no semicolons, single
quotes (double for JSX attributes), parentheses around single arrow-function
parameters, no tabs. That uniformity currently rests entirely on people and
review. Measured, line widths run p50=35, p90=81, p95=83, p99=103 — so "roughly
80, occasionally up to 110" is an established fact that nothing has written
down.

The problem is not how it looks today; it is that **there is no referee**. A
disagreement about style can only be settled by argument in review, one lapse of
attention sinks into the trunk, and this repository runs at 33% comment density,
where the shape of a block is itself part of its readability.

**Boundary (explicitly not done)**:

- **No eslint or biome.** What is wanted here is a referee for formatting, not
  for rules. A linter brings in a whole body of rules that each need deciding,
  and that is a separate change.
- **Markdown is not touched.** See §3.
- **No behaviour changes.** After this, `git diff` should contain no semantic
  change anywhere.

## 2. The plan

### 2.1 Configuration

`.prettierrc.json` at the root:

```json
{
  "semi": false,
  "singleQuote": true,
  "printWidth": 110,
  "trailingComma": "all",
  "arrowParens": "always",
  "endOfLine": "lf"
}
```

Every entry is **measured**, not copied: `semi`, `singleQuote` and `arrowParens`
restate the existing code (289 semicolon-terminated statement lines across the
repository; 1707 parenthesised single-parameter arrows against 419 bare), and
`printWidth` is §3.1.

### 2.2 Scope

Format `.ts` / `.tsx` / `.mjs` / `.json` / `.css`, and **do not format `.md`**.

`.prettierignore` excludes build output (`dist` / `out` / `build` / `release` /
`node_modules`) and all `*.md`.

### 2.3 Entry points

Root `package.json`:

```
"format": "prettier --write .",
"format:check": "prettier --check ."
```

`format:check` hangs off the `test` script alongside the existing
`check:vocabulary` — "testing" in this repository has always included structural
checks, and formatting is the same kind of thing. A rule with no referee is not a
rule.

### 2.4 The one-time reformat

Run `--write` across everything once, as its own commit, mixed with no logic
change.

## 3. Trade-offs

### 3.1 printWidth: why 110

Four candidates, each run as a full reformat in a detached worktree, measuring
`.ts` / `.tsx` / `.mjs` only, against one quantity — **the size of the change**:

| printWidth | files changed | insertions | deletions |
| ---------- | ------------- | ---------- | --------- |
| 90         | 518           | 19788      | 6057      |
| 100        | 426           | 9861       | 3606      |
| **110**    | **364**       | **5031**   | **3377**  |
| 120        | 406           | 3735       | 4669      |

110 is the trough, and it is the **only one small at both ends**. That is not a
coincidence: the author's actual ceiling sits around there (p99=103, with 1,960
lines between 100 and 110). 90 and 100 are forcibly splitting what the author
wrote on one line, and 120 does the reverse — it has the highest deletion count,
because it is **joining lines the author folded by hand**, and those folds are
usually deliberate.

So this is not "pick a nice number", it is **writing down an established fact**.
The cost: 110 is wider than the common 80 or 100, and new code may legitimately
run wider than the current code does. Accepted, because the real constraint on
readability here is the comments (already folded around 88), not the code lines.

### 3.2 Why Markdown is not formatted

It was tried, and the conclusion is **damage**: 2,462 lines changed across 62
documents, almost all of it tables. prettier pads table columns to align them,
and it computes CJK width by code point rather than by display width, so the
technology-stack table in `docs/PLAN.md` is blown out to a single line hundreds
of columns wide with every Chinese column misaligned — a table that was compact
and aligned to begin with.

The benefit in exchange is zero: these documents are hand-written and hand-folded,
with no machine-generated part that needs normalising.

Setting `proseWrap` to `never` or `always` does not save the tables, and
`--embedded-language-formatting` does not reach them. The only answer is to keep
it away from `.md`.

### 3.3 Why CSS is formatted

`styles.css` (2,492 lines) and `db-neo4j/ui/style.css` change 11 lines between
them, and what changes are **real errors**: a section-banner comment at
`styles.css:2208` is indented one space further than the two around it, and there
is a stray blank line at the end of the file. Both are hand-written stylesheets
carrying long explanations, and prettier does not fight them — including them is
free money.

One thing to note: the font stack for `--font-ui` gets joined onto one 110-column
line. That is a direct consequence of §3.1's number, not something specific to
CSS.

### 3.4 Why eslint is not adopted along the way

Formatting and rules are two different things. Formatting is uncontroversial (any
arrangement runs); rules are not — `no-floating-promises`, `exhaustive-deps` and
their kind each need a decision, against this repository's actual style, about
whether to enable them and at what level. This change settles the uncontroversial
half of "there is no referee" and leaves the contested half to its own document.

### 3.5 `git blame` gets washed out

A commit touching 375 files points `git blame` at itself for every one of those
lines. The remedy is `.git-blame-ignore-revs`, which needs the formatting
commit's own hash and therefore can only be added afterwards — it has been, and
the file at the repository root holds the hash of `chore: adopt prettier`.

Measured (`bus/__tests__/layout-ops.test.ts`, which the reformat changed by 185
lines): without the ignore file, 185 lines attribute to the formatting commit;
with it, one does. That remaining line is the kind prettier rewrote thoroughly
enough that git cannot find its ancestor — an inherent residue of this approach.

GitHub honours the file automatically; locally it takes one command:

```
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

`git config` writes to `.git/config`, which is not versioned, so **every clone has
to run it once**.

## 4. Verification

The reformat's actual size: **377 files, +5116 / −3491** (more than §3.1's 364;
the difference is `.json` / `.css` and 18 dead exports removed in the same
round). All four checks were run:

1. `pnpm -r typecheck` — ✅ all seven workspace projects green. Formatting does
   not change meaning, so any red says prettier touched something it should not
   have.
2. `pnpm test` — ✅ 2,543 passing, 0 failing (core 165 / neo4j 71 / redis 41 /
   qdrant 38 / postgres 60 / sql 83 / desktop 2085). **This is the important
   one**: the repository carries a set of tests and guards that **read the source
   itself** (`check-package-vocabulary.mjs`, `audit-shipped-css.mjs`,
   `verify-chat-security.mjs`, `cascade-order.test.ts`, `theme-contrast.test.ts`,
   and the subpath-purity family), matching source files and build output with
   regular expressions. Rearranging code can make one of those stop matching —
   which is not the formatter's fault, but has to be caught on the spot. **Not
   one stopped matching.**
3. `prettier --check .` — ✅ exit code 0.
4. `git diff --name-only | grep '\.md$'` — ✅ zero, `.md` untouched.
