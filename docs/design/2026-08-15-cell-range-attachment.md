# Putting a rectangular selection into the conversation: the `cells` attachment

## 1. What this fixes

### Where things stand

A rectangle dragged out in the grid (`CellRange`,
2026-08-14-grid-drag-selection.md) has exactly one outlet: the clipboard. Right
click inside the rectangle and the menu offers "Copy N cells"
(`DataGrid.tsx:960`), and that is the end of it.

The lower half of that same menu is the "add to conversation" group, generated by
`contextActionsFor` (`context-actions/descriptors.ts:164`), and the finest
granularity it can offer is:

- `cell` — **the one** cell under the pointer;
- `rows` — the selected **whole rows**, every column.

Which is to say: a user who has boxed 3 columns × 40 rows and wants to ask the
model "what is going on with this data" has two routes — add it a cell at a time,
or send the whole rows (possibly 40 columns, 37 of which they are not looking at).

### The problem

Drag selection is a gesture built on 14 August, and the "add to conversation"
descriptors were settled before it; the two were never joined up. In a table
client, "box a block and ask a question" is as natural an action as "box a block
and copy it away", and today only the latter exists.

### This overturns an existing record

`2026-08-14-grid-drag-selection.md` §1 put this inside the not-done scope, and the
reason §3 gives is:

> `ChatAttachment`'s contract is "one view plus a set of row indexes", and main's
> `resolveAttachment` re-reads those rows by offset/limit. Making it accept a
> subset of columns amounts to requiring every driver's read path to support
> projection, which is a data-plane change, far beyond the boundary of an
> interaction fix.

**That reason is wrong**, and the counter-example is in the very file it
describes. `resolveCell` at `resolve.ts:317` already performs a column
projection: it calls `readResultRows` to read **whole rows** just the same, then
locates the column with `findIndex(c => c.name === a.column)` over
`slice.columns`, and takes the value from `row[colIndex]`. The column trimming
happens after main has the rows — a pure in-memory operation the driver knows
nothing about, with nothing pushed down to the data source.

Writing that passage imagined "a subset of columns" as a projection pushed down to
the data source, when the implementation actually sits a layer above. A
rectangular selection wants the same thing, only "pick one column" becomes "pick a
few" and "one row" becomes "a contiguous run of rows".

The sentence "its only downstream is the clipboard" at the top of `cellRange.ts`
has the same origin as `selection.ts`'s note on the division of labour, and both
are corrected here — the two modules stay apart, but the reason is no longer "one
goes to the agent and one to the clipboard"; it is the one §3.5 gives.

### This round's boundary

**Three things are done**:

1. a new `cells` attachment kind (a contiguous row interval × a named subset of
   columns), which main resolves into a small table;
2. wiring it into the context menu;
3. a new renderer-level **selection channel** (`gridSelectionStore`), so places
   outside the grid can know "what is selected right now", and an `@选区` /
   `@selection` entry in the `@` list.

The third is the real structural change here, and it is at the same time the
foundation `Cmd+L` needs — see §2.5.

**Not done**:

- No attachment for non-rectangular selections. Multiple rectangles do not exist
  in the first place (drag-selection §1 already excluded them).
- No change to the contract of `rows` / `result` / `cell`, any of them.
- **No `Cmd+L` key binding.** This round provides only the function it would call
  and the store it would read; key resolution and the integration with
  `useGlobalKeys` / `shortcuts.ts` are a separate change. The reason for the split
  is in §2.5.
- No full-value retrieval for a rectangle attachment. The `cell` kind calls
  `fullValueText` on a truncated value to fetch the whole of it from the source
  (`resolve.ts:345`); a rectangle does not: 40 cells means 40 round trips to the
  driver, and the intent behind boxing a block is to see its **shape**, not the
  full text of one long value. Long values inside a rectangle keep the existing
  truncation marker, and getting the full text means attaching that one cell on its
  own.

## 2. The plan

### 2.1 The contract: a closed interval for rows, names for columns

`ChatAttachment` in `packages/core/src/chat.ts` gains one branch:

```ts
| { kind: 'cells'; viewId: ViewId; resultId: ResultId; r0: number; r1: number; columns: string[] }
```

`ChatAttachmentSpecSchema` in `commands.ts` gains the matching zod branch.

Two decisions worth writing down:

**Rows are an `r0`/`r1` closed interval, not a `rowIndexes` array.** A rectangle
is contiguous by definition, and flattening it into an array of indexes would both
leave a 500-row selection sitting in the Workspace as 500 integers (`chat.ts:319`'s
"a descriptor is not a payload" applies directly) and make `cells` and `rows` look
alike in the type while meaning different things — `rows`'s index array is
**hand-picked scattered rows**, which is the whole of why it exists. The closed
interval lines up with `CellRange`'s `r0`/`r1`, inclusive at both ends; the top of
`cellRange.ts` explains why the entire grid uses closed intervals.

**Columns are an array of names, not an index interval.** Consistent with the
`cell` kind, and for the same reason: a result may be re-run with a different
projection (`resolve.ts:332`'s error copy is about exactly this), after which a
column index points at a different column with no way whatsoever of noticing; when
a column name fails to match, at least `NOT_FOUND` can be reported and the user
knows what happened. The cost is that a rectangle is natively a contiguous
`c0..c1`, and turning it into an array of names throws the "contiguous" part away
— which does not matter, because not one place downstream has a use for it.

The order is the rectangle's, left to right: the order the user sees on screen.

### 2.2 The renderer: one more target field, one more action kind

`ContextTarget` (`descriptors.ts:62`) gains:

```ts
/** The rectangular selection the right-click landed inside, 2×1 and up. */
cellRange?: { r0: number; r1: number; columns: readonly string[] } | undefined
```

The conditions under which `DataGrid` fills it are **exactly the same** as for the
"Copy N cells" item (`DataGrid.tsx:960`): a rectangle exists, the cell count is >
1, and the right-click landed inside the rectangle. All three are required, and
the last is an existing record (drag-selection §2.2.1): what the menu acts on must
be the block the user is pointing at.

A 1×1 rectangle does not fill this field — `target.cell` is already describing
that case, and having both kinds appear would be two accounts of one cell.

`contextActionsFor` gains a `cells` kind, placed before `cell` (the two are
mutually exclusive, so it is in fact the same position), following the existing
"ordered by how specific it is".

### 2.3 The row limit: clamp, and say so

A rectangle's row span is capped at `MAX_SELECTION_SPAN` (20,000), which is the
clipboard's order of magnitude. The attachment side's is
`MAX_CHAT_ATTACHMENT_ROWS` (500), which binds both `rows` and `result`.

Box 3,000 rows and right-click, and the handling is **not** to hide the menu item:
a menu item that disappears does not explain why it disappeared. It is offered as
usual, `r1` is clamped to `r0 + 499`, and the menu copy and the chip copy report
the real numbers — "Add the first 500 rows of this block (3,000 in all)". This is
the same device as the `result` kind's "Add the first 200 rows"
(`descriptors.ts:205`): **the limit appears in the line of text the user reads**,
rather than happening behind their back.

Columns have no limit. The column count is decided by the schema and is bounded
already.

### 2.4 The main side: `resolveCells`

`resolve.ts` gains a branch whose shape sits between `resolveRows` and
`resolveCell`:

1. `span = r1 - r0 + 1`, and anything over `MAX_ROW_SPAN` is `failed` outright
   (the same guard as `resolveRows`; the renderer has clamped already, so this is
   the line of defence against an MCP caller);
2. `readResultRows({ resultId, offset: r0, limit: span })`;
3. locate every name in `columns` as an index into `slice.columns`. **If not one
   of them matches, `failed`**, reporting the same "the projection changed" error
   as `resolveCell`; a partial match carries on, and the missing columns go into
   the notice;
4. trim each row by the matched indexes into a `TabularSlice` and hand it to
   `renderTabular` — the same rendering path `resolveRows` uses, so in the model's
   eyes a rectangle is an ordinary small table;
5. `rowLabel` reads `rows r0–r1`. An interval works here, where `resolveRows` needs
   `summarizeIndexes`, precisely because a rectangle is contiguous.

One more URI, `resultCellsUri`:

```
peek://result/<id>/cells?r=<r0>-<r1>&c=<column names, comma separated>
```

When there are so many column names that readability breaks, it degrades to
`?c=n<count>` by the same rule `resultRowsUri` applies to a long list of indexes
(the comment at `uri.ts:39` is where that rule comes from).

### 2.5 The selection channel: `gridSelectionStore`

#### The obstacle

`range` and `rowSelection` are both `useState` inside the `DataGrid` component
(`DataGrid.tsx:228`, `:245`). The context menu can read them only because the menu
grows inside that subtree. The composer is in another subtree, and
`attachCandidates(views, t)` (`attachments.ts:209`) can only derive its candidates
from the Workspace's `ViewState` — **the selection is not in there**, so `@`
structurally cannot ask about it today.

`Cmd+L` ("add what is selected to the conversation") asks the same question. Two
features are stuck in the same place.

#### A channel, but not the Workspace

A new `state/gridSelectionStore.ts`, a renderer-local single-value store with
subscription:

```ts
type GridSelectionSpec = Extract<ChatAttachmentSpec, { kind: 'rows' | 'cells' }>
```

**What it holds is a descriptor that can be attached as it stands**, with no
wrapper around it. The first draft wrapped it in `{ viewId, spec, summary }`:
`viewId` is already in both specs, and of `summary`'s three fields (row count,
column count, source view name) the first two can be computed from the spec
(`selectionRowCount` / `selectionColumnCount`), while the third is a localised view
name — stored, it becomes a stale string the moment the language changes, and the
place that reads it (`attachCandidates`) is holding `views` anyway, so looking it
up on the spot is the answer that is right. A wrapper layer that is entirely
redundant or wrong; deleted.

`DataGrid` writes on a change of selection, and clears on unmount, on a change of
result, and when the selection is emptied (**clearing only when the value there is
its own**, or two grids selecting in turn would wipe each other).

**Not in the Workspace**, for three reasons, the same one as `Composer`'s "the
draft does not go through the Command Bus" (`Composer.tsx` §"The draft is the one
thing that stays local"):

1. one drag passes through dozens of intermediate selections, and every one of them
   would become a patch broadcast;
2. `read_workspace`'s readers (MCP, the agent) have no use whatsoever for "which
   cells the user has boxed at this instant" — by the time it matters, it has
   already been sent as an attachment descriptor;
3. it needs no persistence. Close the window and reopen it, and the selection ought
   to be empty.

#### One slot, not a map

The store keeps only **the grid where a selection last happened**, not one entry
per grid. The reason is that the phrase `@选区` / `@selection` holds together only
while it refers to one thing; to distinguish "which table's selection", the user
already has the `@items` kind (the whole result), and that is the entry point that
addresses by view.

#### Row selections and rectangles share the one entry

The two kinds of selection are **mutually exclusive** — drag-selection §2.1 nails
down that only one exists at any moment. So `@selection` does not have to
distinguish which one it means:

- a row selection right now → `spec` is `rows`;
- a rectangle right now → `spec` is `cells`.

This also satisfies "rows or cells, either can be added to the conversation"
exactly: **both routes converge on one entry**, and the user does not have to work
out first which category what they just selected falls into.

Clicking a single cell (a 1×1 rectangle) **publishes too**, as a `cells` of one
row and one column. This does not contradict §2.2's "a 1×1 in the context menu
belongs to the `cell` kind": that says the menu should not give two accounts of
one block of data, whereas the question here is whether "what is currently
selected" exists at all — a cell was clicked, so of course it does. The cost is
that a single cell reached through `@selection` does not fetch its full text from
the source the way the `cell` kind does (§1's boundary); getting a long value's
full text still goes through the context menu.

#### `@selection` in the list

`attachCandidates` takes one more parameter (the current snapshot) and, when it
has a value, inserts one entry at the **front** of the list:

| | |
|---|---|
| token | `选区` / `selection` (following the language; `mentionToken` guarantees no spaces) |
| title | "What is selected right now" |
| subtitle | `items · name、score · 3 行` — which table, which columns, how many rows |

With no selection the entry **does not appear** (rather than appearing greyed
out). This follows the existing record at `descriptors.ts:160`: a capability that
cannot be exercised should be absent, not sitting there greyed.

`identity` is derived from the spec, so when the selection changes the "already
added" judgement changes with it — add block A, reselect to block B, and the menu
does not mistake B for something already attached.

#### The interface left for `Cmd+L`

Exported now, used as-is next time:

```ts
function currentGridSelection(): GridSelectionSpec | null   // one read from outside React
function useGridSelectionStore(...)                          // subscribe inside React
```

The first draft also meant to export an
`attachCurrentSelection(): Promise<boolean>`, and it was not built, **which is
deliberate**: actually attaching an attachment goes through the disclosure dialog
(`useContextActions`'s consent gate, which *holds* the user's gesture until the
dialog has been read), and that is React state. Letting the store attach on its
own means either copying the consent gate into the store, or degrading past it —
and neither is acceptable.

So the shape of the `Cmd+L` change is: add a chord in `shortcuts.ts`, take
`useContextActions().add(...)` at the `useGlobalKeys` call site that is **already
inside React**, and build the attachment on the spot with
`stageableAttachment(currentGridSelection(), …)`. One more step, but there is only
one consent gate.

**With no selection, do not swallow the key** — `resolveShortcut`'s existing
convention is that an unclaimed key passes through untouched, and `Cmd+L` means
something else in both a browser and a terminal.

Doing it separately rather than all at once, because the shortcut has to touch
`shortcuts.ts`'s global key table, which carries constraints of its own
(`ctx.textEntry`'s routing, and collisions with macOS menu accelerators —
drag-selection §4.1 recorded the open risk of `⌘C` being eaten by the Edit menu).
That is an alignment of its own, and does not belong stuffed into this one.

## 3. Trade-offs

### 3.1 Why not reuse `rows` with an optional `columns`

The change surface really is smaller — not one type branch to add. It was not
chosen because `rows`'s meaning would become "these columns of these rows", where
its current meaning, "these rows the user hand-picked (whole)", is stated outright
by `resolveRows`'s implementation and its `rowLabel` (`rows at indexes 3, 7, 19`).
With two entry points sharing one kind, every consumer afterwards — resolve, the
URI, the chip copy, MCP's schema documentation — has to branch first on whether
`columns` is present, which merely moves the if out of the type and into every
place of use. This is precisely the reason drag-selection §3 refused to merge the
two selection states, and it applies here for the same reason.

### 3.2 Why not send whole rows and let the model pick the columns

"Three columns were boxed, so send those 40 rows whole — the model will read the
columns it wants anyway" — no, and the reason is budget. `ContextBudget` trims by
characters, and of a row's 40 columns 37 are ones the user is not looking at; they
crowd out the row count that should have been sent, so a 40-row selection is
trimmed to 12 and the user does not know why. The shape the user boxed is itself a
statement of intent, and sending exactly that is both the cheapest and the most
honest thing to do.

### 3.3 `@selection`: an entry point once judged "structurally impossible"

This document's first draft put the `@` entry point in the not-done scope, on the
grounds that `@` must be followed by a name that can be written into a sentence
(`mention.ts`'s `mentionToken`), and "these 16 highlighted cells" has no such
name, so a rectangle could only come in from the menu — and it wrote that "this is
not a functional gap that can be filled in later; it is structural".

**That sentence reached the wrong conclusion.** Its first half is right (a
rectangle really has no name of its own), but deriving "impossible" from it skips a
step: what `@` needs is **a word that can refer to it**, not a name grown out of
the data. "What is selected right now" is such a word, and it is already an
established concept in every piece of spreadsheet software. What was actually in
the way was never the naming, it was §2.5's store — the selection simply could not
reach the composer. The first is an imagined wall and the second a real one, and
the first draft saw only the first.

This note is kept because it is the same kind of error as the one overturned in
§1: **writing "I did not think of how to do it" as "it cannot be done"**. Both
happened during the design phase of one change.

### 3.4 Why `@selection` is not split into one entry per view

One entry per grid holding a selection, with the view name as the token
(`@items`), was considered. It was dropped because `@items` is already the token
for the "whole result" kind, and two entries under one name can be told apart in
the list only by their subtitles — the very line of text that is most easily
skipped. The word `选区` / "selection" carries "there is just one" in itself, and
it refers to the same thing `Cmd+L` does — two entry points sharing one mental
model is worth more than one more addressing dimension.

### 3.5 So why are `cellRange.ts` and `selection.ts` still separate

The old account was "one goes to the agent, one to the clipboard", and after this
round it does not hold. They stay separate, on the sturdier reason that was there
all along (drag-selection §3 in fact already wrote it): a row selection may be
discontiguous and a rectangle is contiguous by definition; the two are mutually
exclusive, but mutual exclusion is a rule about **writing**, not a reason to stuff
two shapes into one union type.

## 4. Verification

Automated:

- `context-actions`'s descriptor tests: with `cellRange` filled in, the `cells`
  kind appears and the `cell` kind does not; at 1×1, the reverse; over
  `MAX_CHAT_ATTACHMENT_ROWS`, `r1` is clamped and the label reports the real total.
- the resolve tests in `main/agent/context/__tests__`: an ordinary rectangle
  renders as a small table with a header; `failed` when no column name matches; a
  notice when only some fail; `failed` when `span > MAX_ROW_SPAN`.
- `gridSelectionStore`'s tests: a write reads back; null after a change of result
  or an emptied selection; grid A clearing after grid B has written **does not**
  wipe B's value (the "only clear your own" rule).
- `mention.test.ts` gains: with a selection, `@selection` is first among the
  candidates, and with none it does not appear; `identity` changes when the
  selection does (so "already added" is never misjudged).
- the existing `chat.test.ts` / `grid-copy.test.ts` must keep passing (neither path
  was touched).

By hand (connected to `peek_test.items`):

1. Box `name`+`score`, two columns × 3 rows → right-click inside the rectangle →
   the menu holds both "Copy 6 cells" and "Add these 6 cells"; click the latter and
   the chip appears above the composer.
2. Send a message → what the model receives is a 3-row table of the `name` and
   `score` columns only, with no `id`/`qty`.
3. Right-click a cell **outside** the rectangle → the rectangle is cleared
   (drag-selection §2.2.1) and the menu becomes the `cell` kind for that one cell,
   with no `cells`.
4. Click a single cell (1×1) and right-click → only the `cell` kind, worded "Add
   <column> row N".
5. Box more than 500 rows → the menu copy reports "the first 500 rows (N in all)",
   and after sending, the model receives 500 rows.
6. Attach, then re-run the query with a different projection (`SELECT id FROM ...`)
   and send → the attachment reports the columns as not found, rather than silently
   sending the wrong ones.
7. Box a block → type `@` in the composer → the first entry is "What is selected
   right now", its subtitle carrying the table name, the column names and the row
   count; pick it, the chip appears, and `@选区` is left in the draft.
8. Reselect another block → type `@` again → the first entry's subtitle follows,
   while the previous block's chip is still there (it is an independent attachment
   already, and does not follow the selection).
9. Select several **rows** (not a rectangle) → type `@` → the same entry is still
   there, its subtitle giving a row count and saying nothing about columns; add it
   and send, and the model receives whole rows.
10. Clear the selection (click empty space) → type `@` → this entry disappears, and
    the rest of the list is unchanged.
